# План 4d. Сборка с IMEI, доставка, рабочее место оператора — план реализации

> Выполняется по задачам, каждая через TDD: тест → падает → код → проходит → коммит.

**Goal:** Оператор видит все заказы по этапам с таймерами, собирает оплаченный заказ сканом IMEI с отметкой UzIMEI, передаёт курьеру и отмечает доставку; поставщик присылает IMEI своего устройства в бот; без IMEI и UzIMEI заказ не отгружается; покупатель видит курьера или трек-номер.

**Architecture:** `orders/fulfilment.py` — сборка: привязка устройств (`InventoryUnit.order_line`), проверки перед отгрузкой, списание остатков. Новое приложение `delivery`: `Shipment` и адаптеры `CarrierProvider` — свой курьер (имя и телефон) и служба доставки вручную (название и номер накладной); адаптер с API службы — когда служба будет выбрана. Рабочее место оператора — страницы в Django Admin (а не отдельный React-экран из спецификации): вход, права и CSRF уже есть, кода в разы меньше.

**Спецификация:** раздел 3.2 п. 4 (IMEI), раздел 5 (PICKING → HANDED_TO_CARRIER → DELIVERED), раздел 6 P0 (рабочее место с SLA-таймерами, приёмка/сборка, доставка: одна служба + свои курьеры).

## Global Constraints

Все ограничения Планов 1–4c действуют. Дополнительно:
- Поштучный учёт (`Category.is_serialized`): на каждую единицу строки — своё устройство с верным IMEI (Луна); отгрузка — только когда все устройства привязаны и отмечены «зарегистрирован в UzIMEI» (проверка UzIMEI на старте ручная).
- Свой склад: скан должен найти устройство этой модификации на складе — опечатка не создаёт новое устройство. Товар поставщика: IMEI создаёт устройство (приёмка при передаче), повтор IMEI запрещён.
- Остаток списывается при передаче курьеру: устройства → «Продан», резервы снимаются, своё предложение пересчитывается по устройствам на складе, у остальных предложений количество уменьшается.
- Отмена во время сборки возвращает свои устройства на склад; устройства поставщика, созданные под заказ, удаляются.
- Действия оператора — POST с CSRF, только у сотрудника с правом изменять заказы; все переходы — через машину состояний с проверкой под блокировкой.

## Задачи

### Task 1. Сборка: устройства и правила
- `InventoryUnit.order_line`; `start_picking` (PAID/SIGNED/COD → PICKING), `add_unit(line, imei, uzimei_registered)`, `remove_unit`, `mark_uzimei`, `picking_problems(order)`.
- Тесты: свой склад и поставщик, чужая модификация, проданное устройство, лишнее устройство, неверный IMEI, повтор IMEI.

### Task 2. Доставка
- `delivery.Shipment(order, carrier, courier_name, courier_phone, tracking, cost_uzs, handed_at, delivered_at)`; `ship(order, carrier, details)` — проверки сборки, переход, списание остатков; `deliver(order)`.
- Отмена при сборке возвращает устройства. Покупателю: «Передан курьеру: имя, телефон» или «Номер накладной»; в заказе на сайте — блок доставки.
- Тесты: отгрузка без IMEI/UzIMEI запрещена, списание своих и поставщика, отмена при сборке, доставка.

### Task 3. Рабочее место оператора
- Админка → «Рабочее место оператора»: этапы (ждут поставщика, ждут оплаты, собрать, собираются, у курьера) с таймерами SLA (поставщик 2 ч, цена 30 мин / 12 ч, сборка 4 ч), кнопки действий, автообновление.
- Страница сборки: адрес, телефон, комментарий; поле IMEI под сканер (Enter), отметка UzIMEI, передача курьеру.
- Тесты: доступ только сотруднику с правом, CSRF, все действия, ошибки показываются сообщением.

### Task 4. IMEI от поставщика через бот
- Сборка началась → поставщику: «Заказ … собираем — пришлите IMEI каждого устройства сообщением».
- Сообщение `356938035643809` или `SG000013 356938035643809` → устройство привязывается к самому старому заказу этого поставщика без IMEI (или к указанному).
- Тесты: привязка, неверный IMEI, чужой заказ, всё уже прислано.

### Task 5. Витрина и проверка
- Страница заказа: курьер / номер накладной. Полные тесты бэкенда и фронтенда, e2e витрины, скриншоты рабочего места.
